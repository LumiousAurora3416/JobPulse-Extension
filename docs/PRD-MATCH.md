## 1. 背景与目标

### 1.1 背景
JobPulse 目前已打通「插件抓取岗位 → 一键写飞书投递表 → agent 跟进提醒 → 归因周报」的投递闭环。但**投递决策本身没有依据**：用户靠感觉判断"这个岗位值不值得投"，导致：

- **海投效率低**：简历与岗位不匹配的投递占用时间，也拉低简历通过率
- **简历版本管理缺失**：针对不同方向/行业，应该用不同版本的简历，但当前没有多版本管理的载体
- **简历没有随投递迭代**：简历被拒后没有系统性的"为什么不够匹配、怎么改"的反馈

### 1.2 目标
在**投递决策点**提供「该不该投 + 为什么 + 怎么改」的即时依据：

1. 投递前快速评估 **JD 与所选简历版本的匹配度**，给出可解释的分数
2. 高分 → 直接投递；低分 → 提供**紧扣 JD 的简历优化建议与改写稿**
3. 建立**多版本简历库**，支持"原始版 → 各方向优化版"的版本链沉淀
4. 匹配度能力**独立可用**，可脱离 JobPulse 作为共享工具

### 1.3 一句话定位
> 在投递决策点，用「分维可解释的匹配度」告诉你该不该投、差在哪、简历怎么改。

## 2. 竞品与参考调研

产品落地前对 GitHub 开源项目做了调研，结论用于校准本设计（详见技术架构文档 §2）。

### 2.1 直接可借鉴的项目

| 项目 | 参考价值 |
|---|---|
| [ApplyRight-AI](https://github.com/Rowe83/ApplyRight-AI) | **章节 Diff 左右对照**（原文 vs 优化稿）；自托管 + 自带 API Key；PDF 上传 + JD 粘贴 —— 与"独立网页 + 优化"形态最接近 |
| [Resume-Matcher](https://github.com/srbhr/Resume-Matcher)（2.7 万星） | Next.js + FastAPI 前后端骨架；简历-JD 量化匹配；多模型（含 DeepSeek）可切换 |
| [Career-Ops](https://github.com/)（41.7K 星） | **A-F 评分 = 10 个加权维度** —— 印证"分维度加权"是主流做法 |
| [ResumeIQ](https://github.com/ayush-s-tomar/ResumeIQ) | 0-100 打分 + 技能缺口标记；**15 组人工标注平均误差 5 分** —— 证明匹配度是可评测、可校准的 |
| [@resurank/scoring](https://www.npmjs.com/package/@resurank/scoring) | **60% 语义嵌入 + 40% TF-IDF 纯算法混合评分** —— 不靠 LLM 的可解释评分路径，可作辅助核对层 |
| [ai-job-search-cn](https://github.com/sunyet-01/ai-job-search-cn) | 中国化 7 维评估框架；"贴 JD 拿三样产物"极简交互；**诚实原则**（AI 不虚构简历经历） |
| [resume-reviewer-ai](https://github.com/kavinithi-sera/resume-reviewer-ai) | 10 分制（ATS 兼容/清晰度/影响力/JD 相关度）；**逐章节分析、原文高亮、简历-JD 差距对比** |
| [BossHunter](https://github.com/powerycy/BossHunter) | "AI 提效 + 人工决策"哲学（AI 生成内容但绝不代替投递）；可恢复性流水线 |

### 2.2 提炼的产品设计原则（本模块采纳）

1. **评估先行、诚实原则**：AI 评分和改写只基于简历实际内容，**不虚构经历**；缺口如实标注
2. **可解释优先**：分数必须伴随"为什么"（维度理由 + JD 命中表），不能是黑盒
3. **决策权在用户**：AI 给建议和改写稿，投递/发送动作由用户执行
4. **本地优先 / BYOK**：自配 API Key、数据不出本地 —— 与共享场景兼容
5. **多版本而非覆盖**：简历库版本独立，优化稿另存新版本，形成可回退的版本链

## 3. 用户与场景

### 3.1 用户画像
- **主用户**：正在进行求职投递的求职者（校招/社招），有多个求职方向（如前端 + 产品并行）
- **次级用户**：同样在秋招/求职、需要评估岗位匹配度的人（分享场景）

### 3.2 核心场景

**场景 A：投递决策（主场景）**
> 用户打开某公司职位详情页，插件抓到 JD 和岗位信息。投递前想知道"我这个岗位值不值得投、我的简历合不合适"。

**场景 B：简历版本管理**
> 用户有前端版、产品版等多个简历版本，需要集中管理，投递时按岗位方向选用最合适的版本。

**场景 C：简历优化**
> 匹配度低时，用户想知道"我的简历哪一段、怎么写不够匹配"，并获得紧扣 JD 的改写建议，改完沉淀为新的简历版本。

**场景 D：独立使用/分享**
> 用户想把这个匹配度能力分享给同学，或脱离 JobPulse 单独使用（粘贴 JD + 简历即可评估）。

### 3.3 用户故事

- 作为求职者，我希望**打开职位页一键算匹配度**，判断该不该投
- 作为求职者，我希望匹配度**能解释**（哪条要求没命中、哪段经历不行），而不只是一个数字
- 作为求职者，我希望匹配度低时**拿到紧扣 JD 改写的实习/项目经历稿**，直接改
- 作为求职者，我希望改完的简历**另存为新版本**，下次投递直接选优化版
- 作为求职者，我希望这个工具**能独立用、能分享**，不依赖插件也能粘贴 JD + 简历评估

## 4. 功能需求（分阶段）

### V1 · 投递闭环（MVP）

**目标**：投递前能选简历版本、算匹配度、高分直接投。

| # | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F1 | **简历库（飞书新表）** | 多版本简历存储。每行一个版本，字段：简历名称、适用方向、简历正文、来源版本、创建/更新时间 | P0 |
| F2 | **简历版本管理入口** | 提供简历库的新增/编辑入口（先做后端接口，UI 后置到 V2） | P0 |
| F3 | **插件匹配度按钮** | 职位详情页弹窗新增「匹配度计算」按钮：选简历版本 → 调后端算分 → 显示分数 + 摘要 | P0 |
| F4 | **匹配度评分引擎** | 结构化分维度评分（见技术架构 §3），返回分数 + 维度理由 + JD 命中表摘要 | P0 |
| F5 | **高分直接投递** | 匹配度 ≥ 阈值（默认 70，可配）时，一键走现有投递流程写入飞书 | P0 |

**V1 验收标准**：
- 插件弹窗可选简历版本并显示匹配度分数，分数有维度理由可展开
- 匹配度 ≥70 可一键投递，写入投递表
- 简历库支持多个版本独立存取，互不覆盖

### V2 · 优化闭环（核心差异化）

**目标**：低分时能看依据、拿改写稿、沉淀新版本。

| # | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F6 | **联动优化网页** | 与数据看板、agent 并列的新页面，插件快捷入口可跳转；**与插件联动**（自动带入抓到的 JD、选中的简历版本），**也可独立使用**（手动粘贴/上传 JD 与简历） | P0 |
| F7 | **得分依据展示** | ① JD 要求命中表（每条要求 ✅/❌ + 证据）；② 各维度得分与理由；③ **逐段简历诊断**（尤其实习/项目：这段为什么不够匹配） | P0 |
| F8 | **紧扣 JD 的优化稿** | LLM 改写**实习经历与项目经历**（重点实习），输出**章节 Diff 左右对照**（原文 vs 优化稿），可编辑 | P0 |
| F9 | **另存为新版本** | 优化稿编辑后「另存为新简历版本」→ 写入简历库（**新增行，不覆盖**），命名建议"XX公司-XX岗位-优化版" | P0 |
| F10 | **独立填写模式** | 不经过插件时，网页支持手动填写 JD、上传/粘贴简历即可评估 | P1 |

**V2 验收标准**：
- 网页展示命中表（每条要求带证据）、维度理由、逐段诊断
- 优化稿针对实习/项目经历、紧扣 JD，左右对照可编辑
- 「另存为新版本」写入简历库新增行，原始版本不受影响
- 网页脱离插件可独立评估（手动 JD + 简历）

### V3 · 独立化与分享

**目标**：匹配度能力独立成可分享、可部署的工具。

| # | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F11 | **BYOK 静态页** | 纯静态 HTML + 用户自配 DeepSeek Key（存 localStorage），网页直接调 LLM 评估，零后端 | P1 |
| F12 | **分享与独立部署** | 静态页可部署到任意静态托管，发链接即可分享；可脱离 JobPulse 单独使用 | P1 |
| F13 | **简历文件上传解析** | 支持 PDF/Word 简历上传并抽取文本（需引入解析依赖，放 V3 评估） | P2 |

**V3 验收标准**：
- 静态页在无后端情况下，粘贴 JD + 简历即可出完整评估
- 分享链接在另一台设备可用（对方自带 Key）
- 简历 PDF/Word 上传可正确解析文本

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| 评分稳定性 | 同一 JD+简历 两次评估，总分波动 ≤ ±5 分（用锚点 + 固定 prompt 控制） |
| 评分可评测 | 建 10-15 组人工标注样本作为基准集，校准评分（参考 ResumeIQ 的 MAE 评测法） |
| 响应速度 | 单次匹配度计算 ≤ 15s（LLM 一次调用）；插件侧交互流畅 |
| 密钥安全 | 插件/网页不硬编码 key；BYOK 模式 key 只存本地（chrome.storage / localStorage） |
| 数据隐私 | 简历文本仅在本地与 LLM 调用之间流转，不留存于插件侧 |
| CORS | 独立网页直调 DeepSeek 需验证 CORS 支持；不支持则 V3 增加薄后端代理 |
| 可回退 | 简历库版本链可追溯来源，随时回退到任意版本 |

## 6. 指标与成功标准

- **投递前评估覆盖率**：插件抓取后使用匹配度功能的会话占比
- **简历通过率**（对比接入前后）：有匹配度依据的投递，进入面试的比例
- **简历库版本数**：沉淀的版本链数量（衡量"优化闭环"是否被使用）
- **评估耗时**：从点击按钮到出分的时间

## 7. 开放问题

1. 匹配度阈值（70）是否需要按岗位类型/用户情况动态调整
2. 简历正文放多维表格文本字段的容量与性能边界（超长简历如何处理）
3. V3 是否需要 PDF/Word 解析（依赖选择与体积评估）
4. 是否复用/暴露现有 agent 后端作为"薄后端代理"以规避 CORS
